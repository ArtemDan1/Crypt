# Crypt: дизайн

Дата: 2026-10-28
Статус: черновик на согласование

## 1. Зачем

Сейчас знания об инфраструктуре (серверы, IP, доступы) разбросаны по Obsidian и папкам, а пароли и SSH-ключи лежат отдельно. Что-то уже потерялось. Crypt — **персональное зашифрованное хранилище**, где база знаний (как Obsidian + Anytype) и хранилище секретов (как KeePass) живут вместе: карточка сервера содержит его поля и заметку, а поле «Креды» ссылается на секрет (пароль или SSH-ключ) в том же хранилище.

Критерий успеха: пользователь переносит туда серверы и доступы из Obsidian/папок и больше не ищет их в разных местах. Подключение по SSH идёт через ключ из Crypt с подтверждением Touch ID.

Пользователь один. Общего доступа нет и не планируется в ближайших фазах.

## 2. Цели, не-цели, анти-цели

**Цели MVP (macOS):**
- записи с Markdown-телом, папками и тегами;
- пользовательские типы с полями (например, «Сервер»);
- табличный вид по типу;
- секреты (пароль, SSH-ключ, токен, защищённая заметка) и поле-ссылка на секрет;
- встроенный ssh-agent с подтверждением через Touch ID;
- всё зашифровано, ключ выводится из сид-фразы, быстрая разблокировка через Touch ID или PIN;
- импорт SSH-ключей пачкой из `~/.ssh` (решение пользователя).

**Не-цели MVP (будут позже, см. §10):** синхронизация, iOS, импорт .kdbx и Obsidian, экспорт в .md, UI истории версий, Windows, self-hosted веб.

**Ограничение по бюджету (решение пользователя):** всё должно работать без платного Apple Developer аккаунта. Схемы, которым он нужен, не используем; переход на них позже должен быть возможен без переделки остального (см. §5.4, §10).

**Объём:** сейчас у пользователя сотни записей; закладываемся на тысячи (до ~10 000) без деградации. Загрузка всего хранилища в память и индекс в памяти на таком объёме допустимы (моё решение; исполнитель может выбрать иначе).

**Не делаем вообще (пока):** граф связей, Notion-уровень баз данных (формулы, rollup, связи многие-ко-многим с агрегатами), совместный доступ, плагины.

**Анти-цели (провал, даже если всё «работает»):**
- секрет утёк на диск, в лог, в экспорт или в незашифрованный индекс открытым текстом;
- данные потерялись: при синхронизации, сбое записи, обновлении формата;
- зависимость от облака или стороннего сервера для базового использования;
- приложение медленнее и неудобнее Obsidian в повседневной работе с заметками.

## 3. Стек (решение пользователя)

- **Tauri 2**, фронтенд на **Vue 3 + shadcn-vue** (Tailwind), ядро на **Rust**.
- Сначала macOS. Tauri 2 выбран также ради будущих iOS и Windows. Rust-ядро должно быть отделено от Tauri-слоя (отдельный crate, например `crypt-core`), чтобы позже переиспользовать его в self-hosted сервере и на iOS.

Рекомендации (решение исполнителя, если нет веских причин против):
- редактор: **CodeMirror 6** с live preview, как в Obsidian;
- CRDT: **Loro** (Rust);
- криптография: RustCrypto / `chacha20poly1305`, `hkdf`, `argon2`, `bip39`;
- SSH: crate `ssh-key` / `ssh-agent-lib` или аналог.

## 4. Модель данных

### 4.1 Запись (Record)
Базовая единица. Поля:
- `id` (UUID / ULID), `title`;
- `body`: Markdown-текст (CRDT-текст);
- `folder_id`: одна папка (иерархия папок, как в Obsidian);
- `tags`: список строк;
- `type_id`: опционально, тип записи;
- `fields`: значения полей типа;
- `created_at`, `updated_at`.

Запись без типа — обычная заметка.

### 4.2 Тип (Type)
Пользователь создаёт типы в UI: имя, иконка и упорядоченный список полей. Виды полей в MVP:
- text, number, date, url, checkbox;
- select / multi-select (варианты задаются в типе);
- link-to-record (ссылка на другую запись, опционально ограниченная типом);
- **link-to-secret** (ссылка на одну или несколько записей-секретов).

Изменение типа (добавить, переименовать, удалить поле) не должно ломать существующие записи: значения хранятся по `field_id`, а не по имени. Значения удалённого поля сохраняются скрытыми до явной очистки (моё решение).

Пример встроенного стартового типа: «Сервер» (hostname, IP, ОС, провайдер/локация, SSH-порт, SSH-пользователь, Креды → секрет). Пользователь может его менять.

### 4.3 Секрет (Secret)
Отдельный вид записи (у секрета тоже может быть заметка, папка и теги). Подвиды:
- **Login**: username, password, url, TOTP-seed (опционально, моё решение: хранить можно, генерацию кодов показать, если дёшево);
- **SSH-ключ**: приватный ключ (ed25519, ecdsa nistp256/nistp384, rsa), публичный ключ и комментарий. Пароль зашифрованного ключа используется только при импорте и не сохраняется; внутри зашифрованного хранилища ключ нормализуется в незашифрованный OpenSSH. Новый ключ генерируется как ed25519;
- **Карта**: номер, владелец, срок, CVV и PIN;
- **Token / API key**;
- **Secure note**.

Правила отображения: значения скрыты по умолчанию; «показать» и «копировать» по клику; буфер обмена очищается через 30 с (настраивается); генератор паролей.

В карточке записи поле link-to-secret показывает имя секрета и кнопки копирования (логин, пароль, публичный ключ), не раскрывая значение.

**История секретов (решение пользователя):**
- при **изменении** значения секрета старые значения сохраняются в истории (можно найти прежний пароль);
- при **удалении** секрета он вычищается полностью, вместе со всей историей значений, и (после фазы синхронизации) удаление с вычисткой распространяется на все устройства. Поэтому значения секретов нельзя хранить так, чтобы они навсегда оседали в общей неудаляемой истории CRDT: нужна отдельная гранулярность (например, отдельный документ на секрет, который можно уничтожить целиком) с «надгробием» для синхронизации. Конкретный механизм — решение исполнителя, но формат хранения должен это поддерживать с MVP.
- Удаление обычных записей: корзина с восстановлением (моё решение), полная вычистка не требуется.

**Импорт `~/.ssh` (MVP):** мастер показывает найденные приватные ключи, пользователь отмечает нужные; зашифрованные ключи спрашивают passphrase. Каждый ключ становится секретом «SSH-ключ». Исходные файлы не трогаются, удалять их предлагается отдельным явным действием (моё решение: только подсказка, без автоудаления).

### 4.4 Ссылки
- `[[Название]]` / `[[id|алиас]]` в теле заметки, автодополнение по заголовкам;
- панель бэклинков в карточке: кто ссылается (из текста и из полей link-to-record и link-to-secret).

Переименование записи не ломает ссылки: внутри хранится id (моё решение).

### 4.5 Табличный вид
Для каждого типа: строки — записи, колонки — поля + title, теги, папка. Сортировка, простые фильтры (равно / содержит / пусто), скрытие и порядок колонок, правка прямо в ячейке, создание записи из таблицы. Настройки вида сохраняются. Несколько сохранённых видов на тип — по желанию (не обязательно в MVP).

### 4.6 Навигация
Сайдбар: дерево папок, список типов (клик открывает таблицу), раздел «Секреты», теги. Быстрый поиск / переключатель по Cmd+K (поиск по заголовкам и тексту, без значений секретов). Вкладки или история навигации — по усмотрению исполнителя.

## 5. Хранение и шифрование

### 5.1 Формат
- Все данные хранятся как CRDT-документы Loro: это сразу заложено под будущую синхронизацию и историю версий. Гранулярность (документ на запись + служебные документы для типов и папок, либо иначе) — решение исполнителя, с учётом того, что синхронизация должна передавать только изменения.
- История изменений сохраняется с самого начала (не компактить без нужды), даже если UI истории появится только в фазе 2.
- Каждое изменение помечается id устройства и временем.

### 5.2 Шифрование на диске
- Всё содержимое шифруется (AEAD, например XChaCha20-Poly1305). Открытым текстом на диске может лежать только непрозрачная служебная информация (id файлов, версия формата).
- Индексы для поиска и таблиц (если используется SQLite или подобное) тоже шифруются (SQLCipher) или строятся только в памяти. Значения секретов в индекс поиска не попадают никогда.
- Атомарная запись (temp-файл + rename), чтобы сбой не портил хранилище.
- Расположение хранилища: `~/Library/Application Support/Crypt/` по умолчанию; одно хранилище в MVP.

### 5.3 Ключи
- При создании хранилища генерируется **сид-фраза BIP39 из 24 слов**. Приложение показывает её один раз, проверяет, что пользователь её записал (ввод нескольких слов), и предупреждает: без неё восстановления нет.
- Из сид-фразы через HKDF выводятся независимые ключи: ключ данных, ключ аутентификации синхронизации (на будущее), ключ id хранилища.
- Восстановление и подключение устройства — ввод сид-фразы (или, позже, QR с другого устройства).

### 5.4 Разблокировка (macOS, без платного аккаунта)
Строгая схема (Keychain-элемент с biometry access control) требует data-protection keychain и entitlement-ов, то есть платного аккаунта. Поэтому в MVP (решение пользователя: без платного аккаунта; механика — моё решение):
- **Подпись приложения:** самоподписанный code-signing сертификат, созданный локально (инструкция в README). Подпись стабильна между сборками, поэтому ACL login keychain не сбрасывается при каждой пересборке.
- **Ключ данных** хранится в login keychain (file-based), ACL ограничен этим приложением.
- **Touch ID** проверяется через LocalAuthentication (`LAContext.evaluatePolicy`): это не требует entitlement-ов. Ключ из Keychain читается только после успешной проверки.
- **Нет Touch ID** (Mac без сенсора, закрытая крышка): `deviceOwnerAuthentication`, то есть пароль от Mac.
- **PIN:** минимум 6 цифр. Ключ данных обёрнут ключом из PIN (Argon2id), обёртка хранится в Keychain (не в файлах хранилища, чтобы бэкап или копия диска не давали перебрать PIN офлайн). После 5 неудачных попыток обёртка удаляется, нужна сид-фраза.
- **Известная слабость:** биометрия проверяется приложением, а не Keychain. Вредонос под тем же пользователем теоретически может достать ключ. Принимается для MVP.
- Модуль разблокировки изолирован за интерфейсом, чтобы позже (при появлении аккаунта) переключиться на data-protection keychain с biometry ACL без изменений в остальном коде.

Общее:
- Автоблокировка: по таймауту бездействия (по умолчанию 15 мин, настраивается), при блокировке экрана Mac и при сне. При блокировке ключи стираются из памяти (`zeroize`).
- Сид-фраза хранится зашифрованной ключом данных и показывается повторно только после свежего подтверждения (Touch ID / пароль Mac / PIN), даже если хранилище уже разблокировано (моё решение).

## 6. ssh-agent

- Crypt поднимает свой агент на Unix-сокете `~/Library/Application Support/dev.crypt.app/agent.sock` (каталог 0700, сокет 0600, соединения только от текущего uid). В настройках есть инструкция и кнопка «настроить»: прописать `SSH_AUTH_SOCK` / `IdentityAgent` в `~/.ssh/config`.
- Агент отдаёт публичные ключи всех SSH-секретов, у которых включён флаг «доступен агенту» (по умолчанию включён для новых ключей).
- Каждая операция подписи требует подтверждения Touch ID. Системный диалог показывает, какой ключ и (если известно) для какого хоста или процесса.
- Опция «доверять на N минут» задаётся в настройках (0/1/5/15, по умолчанию 0 = подтверждать каждый раз), но окно доверия действует отдельно на каждый ключ. Блокировка сбрасывает все окна. Подписи сериализуются: одновременно не больше одного диалога; после ожидания доверие проверяется повторно.
- **Работа при заблокированном хранилище (моё решение):** `ssh` сначала запрашивает список публичных ключей и только потом подпись. Поэтому публичные ключи (и флаг «доступен агенту») дублируются в отдельный элемент Keychain без биометрии, и агент отдаёт список, не разблокируя хранилище. Публичные ключи не секретны; утечка ограничивается фактом, какие ключи есть. Запрос подписи при заблокированном хранилище вызывает Touch ID (или пароль Mac), временно открывает Vault для подписи и сразу закрывает его; AppState и интерфейс остаются заблокированными. Если вход по Touch ID не настроен, подпись сразу отклоняется и приложение показывает экран разблокировки. Отмена подтверждения тоже возвращает отказ.
- Чтобы агент работал при закрытом окне, Crypt живёт в строке меню (иконка в menu bar) и может запускаться при входе в систему (настройка).
- Блок Crypt `Host * / IdentityAgent` добавляется в конец `~/.ssh/config`: первые значения OpenSSH сохраняют приоритет для пользовательских Host-блоков. Перед первой записью создаётся `config.crypt-backup`; запись атомарная с сохранением прав, удаление блока сохраняет остальной текст. Закрытие окна прячет Dock и сохраняет агент; явный выход завершает процесс.
- Добавление ключей через `ssh-add` в агент Crypt — не нужно в MVP (только ключи из хранилища).

## 7. UI и UX

Макеты (согласованы): https://claude.ai/artifact/6WNytj3nPs5x1k1EcEEg8U — карточка записи, таблица типа, конструктор типов, секреты, разблокировка, сид-фраза, меню-бар. Тёмная тема shadcn (zinc), шрифт Geist / Geist Mono, единственный акцент — янтарный `#fbbf24` для всего, что связано с секретами. Серверы — лишь один пример типа; ssh-agent — дополнительная функция, не центр интерфейса.

- Тема светлая и тёмная, по системе.
- Окно: сайдбар, основная область (заметка или таблица), справа опциональная панель (поля, бэклинки).
- Карточка записи: заголовок, блок полей типа (редактируемый), редактор тела.
- Онбординг: создать хранилище → показать и подтвердить сид-фразу → включить Touch ID / задать PIN → подсказка по ssh-agent. Стартовых типов онбординг не создаёт.
- Горячие клавиши: Cmd+K (поиск), Cmd+N (новая запись), Shift+Cmd+N (новая папка), Cmd+L (заблокировать), Cmd+, (настройки). Те же команды есть в русском меню-баре macOS.
- Поля секретов редактируются по клику прямо в строке; правая кнопка мыши на записи или папке открывает контекстное меню.

## 8. Безопасность: требования

- Никаких секретов в логах, крэш-репортах, в URL и в фронтенд-хранилище (localStorage) Tauri. Фронтенд получает значение секрета только по явному действию «показать» или «копировать»; копирование лучше делать на стороне Rust.
- Сетевых запросов в MVP нет вообще (никакой телеметрии, автообновление — по решению исполнителя, но без отправки данных).
- Строгий CSP в Tauri, минимальный набор разрешённых команд (Tauri capabilities).
- Rust-ядро покрыто тестами: шифрование/расшифровка, вывод ключей из известной сид-фразы (тестовые векторы), сохранение и загрузка, совместимость формата.

## 9. Что остаётся исполнителю

Структура crate-ов и модулей, гранулярность Loro-документов, способ построения индекса и поиска, детали UI-компонентов, выбор конкретных SSH- и Keychain-библиотек, формат файлов на диске (с номером версии формата), стратегия миграций формата.

## 10. Дорожная карта после MVP (порядок)

1. **Синхронизация Mac ↔ iPhone по LAN.** Обнаружение через Bonjour/mDNS. Устройства одного хранилища аутентифицируют друг друга ключом из сид-фразы. Канал шифруется (Noise или TLS на выведенных ключах), сами изменения тоже зашифрованы, чтобы в будущем self-hosted сервер мог хранить и передавать их вслепую. Обмен идёт в фоне при обнаружении, плюс кнопка «синхронизировать сейчас» и индикатор статуса. Слияние автоматическое через CRDT: текст — посимвольно, поля — последняя запись побеждает, прошлое значение остаётся в истории.
2. **История версий в UI:** по записи (кто, когда, с какого устройства, diff, откат), плюс ручные именованные снимки всего хранилища.
   *Сделано (2026-10-29).* Каждое изменение подписывается видом («текст», «название», «поля»…); правки одного вида с одного устройства в пределах 5 минут — одна версия. Откат записи добавляет версию «Возврат», не трогая секреты, папку и корзину. Снимок хранит версию каждой записи; откат к снимку возвращает содержимое и состояние корзины, более поздние обычные записи кладёт в корзину, секреты не трогает, стёртые навсегда не возвращаются; типы и папки не откатываются.
3. **iOS-приложение** (Tauri 2), Face ID, подключение устройства по QR или сид-фразе. Распространение без платного аккаунта (решение пользователя, предварительное): бесплатный Apple ID (Personal Team) + AltStore/SideStore, переподпись раз в 7 дней. На iOS строгая схема Keychain с биометрией доступна и с бесплатной подписью. Альтернатива на обсуждение в фазе 3: PWA, которую отдаёт сам Mac по HTTPS в LAN (свой корневой сертификат, ядро в WASM; Face ID через passkeys на `.local` под вопросом). Чтобы не закрыть этот путь, Rust-ядро по возможности не должно зависеть от того, что не собирается в WASM (моё решение: мягкое требование, не блокирующее MVP).
4. **Импорт:** .kdbx (KeePass) в секреты; папка Obsidian в записи (frontmatter → поля, если совпадает тип).
